# SimpleSkillWatch

A World of Warcraft: Forever addon (interface 16001) by Gnare: a movable frame of
weapon/Defense, profession and other skill bars, colored by thresholds the player sets.
The README describes every feature as the player sees it; read it first.

## Layout

- `SimpleSkillWatch.toc`: addon manifest (version, SavedVariables, `IconTexture`)
- `icon.tga`: the addon's icon (AddOns list, minimap button): 64x64, 32-bit,
  uncompressed, made from the 512x512 CurseForge icon
- `SimpleSkillWatch.lua`: everything except the settings window: defaults, profiles,
  skill scan, coloring, disarm detection, the frame, events, slash commands
- `CastLog.lua`: the `/sskw castlog` diagnostic (events and lookups around crafting and
  gathering). Loaded between the other two; uses `ns` helpers from the main file.
- `Settings.lua`: the settings window (tabs Frame / Text / Skills / Alerts / Profile)
  and the Options → AddOns entry. Shares the addon namespace `ns` with the main file.
- `Sounds/*.ogg`: the addon's own alert chimes, generated by `tools/make_sounds.py`
  (numpy + ffmpeg; not packaged). Edit the notes there and rerun it; don't hand-edit
  the files. Claude can't hear them: Gnare judges how they sound.
- `tests/`: a mock of the WoW API (`wowmock.lua`) and `test_*.lua` files
- `.pkgmeta`, `.github/workflows/`: packaging and release (see Releasing)

## Testing

There is no WoW client here. Behavior is checked against a mock API in Lua 5.1:

    pip install lupa
    python tests/run_tests.py           # all
    python tests/run_tests.py lock      # files whose name contains "lock"

Run the tests after every change and add a test for each new behavior or fix.
The mock is deliberately small: widgets record what the addon set on them, and unknown
methods are no-ops that return nil. Two traps from that:
- Any missing *field* on a mock widget reads as a function (truthy). Initialize every
  custom field the addon puts on a frame (e.g. `button.dimmed = false`) instead of
  relying on nil.
- Passing tests don't prove it works in game. Say what still needs an in-game check.

Gnare tests in game and reports back, often with screenshots. In-game diagnostics:
`/sskw events`, `/sskw disarmlog`, `/sskw debug`, `/sskw fontinfo`, `/sskw castlog`
(its lines are kept in `SimpleSkillWatchDB.castlog`; `/sskw castlog copy` shows them in
a window he can copy from and paste back).

### How Gnare gets your changes

His `Interface\AddOns\SimpleSkillWatch` folder is a git clone of this repo. He tests
by pulling and typing `/reload` in game, so a change isn't testable until it's pushed.

- When a change is ready to try (tests pass), commit and push it, then end your reply
  with exactly what to run, e.g. `git pull` then `/reload`.
- Push to `main` unless he asks for a branch. Pushing to `main` doesn't publish
  anything (see Releasing).
- If you can only push to this session's own branch, push there and give him the
  commands instead: `git fetch` then `git switch <branch>` (and `git switch main`
  to go back). When he's happy, merge into `main` if you can, or tell him it still
  needs merging (a pull request he merges on GitHub works).
- He can't see the cloud session's files, so never say "the file is ready" for
  something that isn't pushed.

## WoW: Forever API notes (learned the hard way)

- Skills come from `C_SkillInfo` (`GetNumSkillLines`, `GetSkillLineInfo`,
  `GetSkillLineInfoByID`). Lines under a collapsed header aren't returned.
- Many values are "secret" in combat (`issecretvalue(v)`): skill ranks, durability,
  aura and loss-of-control details, `UnitAttackSpeed`, `UnitDamage`. Never compare or do
  arithmetic on a secret value; keep showing the last readable value.
- No combat log for addons.
- Loss of control: only `priority` and `displayType` are always readable. Observed
  priorities (all with `HasFullControl()` true): 1 root (Frost Nova), 2 interrupt /
  school lockout, 3 disarm. Stuns, fears and charms remove control. `displayType`
  follows the player's interface options, not the effect.
  `GetInventoryItemEquippedUnusable` stays false while disarmed.
- Rescans are triggered by `SKILL_LINES_CHANGED`, `CHAT_MSG_SKILL`, `SPELLS_CHANGED`
  (all confirmed to fire); bursts are coalesced into one redraw (0.25 s).
- Professions use the modern `C_TradeSkillUI` (client 1.60.1). The old `GetTradeSkill*` /
  `GetCraft*` globals and `TRADE_SKILL_UPDATE` / `CRAFT_*` events don't exist.
- A craft fires `TRADE_SKILL_CRAFT_BEGIN(recipe)`, then `UNIT_SPELLCAST_SENT/START/
  SUCCEEDED/STOP` with the recipe's spell ID readable, then
  `TRADE_SKILL_ITEM_CRAFTED_RESULT`. A skill-up's `CHAT_MSG_SKILL` comes about 0.4 s
  after `SUCCEEDED`. Nothing fires for a craft that gives no point.
- `C_TradeSkillUI.GetTradeSkillLineForRecipe(recipe)` returns the recipe's own line, its
  name and the profession (`2942, "First Aid", 129`); for the spell that opens the
  window just `129, "First Aid"`. `GetRecipeInfo(recipe).relativeDifficulty` was 1 for
  a yellow recipe and 3 for a grey one (0 orange and 2 green are assumed, not seen);
  `maxTrivialLevel` is the skill where it turns grey. `canSkillUp` and `numSkillUps`
  don't follow difficulty (true and 1 on a grey recipe). The window-opening spell has
  `learned = false`.
- Gathering a herb fires `UNIT_SPELLCAST_SENT` (with the node's name as target), `START`,
  `SUCCEEDED`, `STOP` for the rank's spell (2368 "Herbalism" at Journeyman), which maps
  to the profession (`2944, "Herbalism", 182`) with no window open. That spell is not a
  learned recipe and carries no difficulty; `GetGatheringOperationInfo` returns nil. The
  skill-up's `CHAT_MSG_SKILL` comes right after `SUCCEEDED` (skill still old when
  `SUCCEEDED` fires). The node's difficulty shows only in its tooltip: the line naming
  the profession is colored grey 0.50/0.50/0.50, green 0.25/0.75/0.25, yellow 1/1/0
  (orange not seen). That line is the game's own (confirmed with other addons off). Mining, skinning and fishing not looked at yet.
- Instant spells (opening a profession window) fire `SUCCEEDED` without `START`.
- Don't build on other addons' tooltip text: Gnare runs "Gather Skill Tooltip", which
  rewrites a node's first line (`Silverleaf (103/1)`).
- Minimap shape: no game API. Addons that reshape the minimap define a global
  `GetMinimapShape()` returning `"ROUND"`, `"SQUARE"`, `"CORNER-TOPLEFT"`, … (a
  convention; absent means round). Not yet tried against a real minimap addon.
- Register events through `SafeRegister` (checks `C_EventUtils.IsEventValid`).
- Fonts from other addons may not be loaded at login: `SetFont` can fail or draw blank,
  and re-applying the same face is ignored, so the code switches to the default face and
  back, with timed redraws.
- Forever trainers have no level requirement for profession ranks; TRAIN depends on
  skill only (Journeyman 50, Expert 125, Artisan 200; secondary Artisan 225).
- `/reload` loads a newly installed addon and files newly added to one (a new `.lua` in
  the .toc, `icon.tga`, new sounds); no restart needed. It does NOT re-read a sound file
  whose contents changed: after regenerating an existing `Sounds/*.ogg`, tell Gnare to
  quit and restart the client (or give the file a new name).

## Saved data

- `SimpleSkillWatchDB` (account): `profiles[name]` holds every setting plus `ignored`
  skills; also the settings window position and tab, and the last cast log (`castlog`).
- `SimpleSkillWatchCharDB` (character): `profile`, `pos`, `locked`, `known` skills,
  `minimapAngle` (the minimap button's place, in degrees).
- New characters get a profile named after their class, copied from `Default` if it
  exists. Any change to the saved layout needs a migration on load for older data, and a
  test for it.

## Conventions

- Player-facing text (chat, tooltips, settings, README) is short and plain: say what
  happens, no jargon.
- Credit is "Gnare" (shown in `#4D5FFF` in the settings window).
- Every player-visible change gets a `CHANGELOG.md` line under `## Unreleased` at the
  top (create the heading if missing). Merge
  lines when later work changes or reverts something from the same unreleased batch, so
  the notes describe the end result, not the iterations. Update the README when a
  feature or command changes.
- Versions are major.minor.patch. A version lives in three places that must match:
  `## Version:` in the .toc, the header comment and `ns.VERSION` in
  `SimpleSkillWatch.lua`.
- **Bump the patch number on every push Gnare will test** (1.0.0 → 1.0.1 → 1.0.2 …),
  even for a one-line fix, so the login message in game proves which build loaded.
  Say the new number in your reply. Test builds don't get their own changelog
  headings: their lines stay under `## Unreleased`.
- Before bumping, check the version on `main` (it may have moved since your session
  started) and go one past the higher of the two, so two sessions never ship
  the same number.

## Releasing

Pushing to `main` publishes nothing; only a version tag does.

1. Gnare picks the release number. Either keep the last test build's number (e.g.
   1.0.7), or collect the batch into the next minor or major version (e.g. 1.1.0); set
   it in the three places if it changed. Rename `## Unreleased` in `CHANGELOG.md` to
   `## X.Y.Z`. Skipped patch numbers are fine.
2. Merge to `main`.
3. Tag and push: `git tag vX.Y.Z && git push origin vX.Y.Z`.
   Or, on github.com: Releases → Draft a new release → new tag `vX.Y.Z` on `main` →
   Publish. That tag starts the same workflow, which fills in the release's notes and zip.
   (Cloud sessions can push branches but not tags, so they use this route.)

The Release workflow runs the tests, checks that the tag, .toc, `ns.VERSION` and
changelog agree, then the BigWigs packager builds `SimpleSkillWatch-vX.Y.Z-forever.zip` and
uploads it to CurseForge (project ID from `## X-Curse-Project-ID` in the .toc, key from
the `CF_API_KEY` repository secret) and to GitHub Releases, with that version's changelog
section as release notes. The packager detects Forever from `## Interface: 16001`.
Tags containing `alpha` or `beta` publish as alpha/beta files.
